# Phase 6 — Drills (the differentiator)

> **3–5 sessions.** Owning the corpus is worthless without fluency. The interview is judged on efficiency, clarity of thought, communication, curiosity, and trade-off thinking — every one of those is fluency, not knowledge.

## How to start this session

Open Claude Code in `C:\Users\adsto\git\domains`. Paste this file or say: *"Run domains/_shared/sessions/phase-6-drills.md, drill <n>."*

## Read first
- [`PREAMBLE.md`](./PREAMBLE.md) — re-read the **Interview-day evaluation criteria** section every drill
- The harness's `--help` output

## Goal

Drill until I can:
1. Walk into an unknown bad container/Linux situation and find the root cause in <30 min
2. **Narrate my reasoning out loud** at all times — what I'm checking, why, what would falsify
3. Ask 1+ clarifying question before *acting* (not just before starting)
4. Explain trade-offs in fixes (rollback path, blast radius, time vs. correctness)
5. Cite my sources naturally — "this matches the dockerd troubleshoot page on …"

## Drills

### 6.1 — Cold-call drill (Docker Compose unknown failure)

I create a deliberately broken `docker-compose.yml` (e.g., wrong image tag + insufficient memory + missing env var). Without prior context, I:
- Run it
- Talk through diagnosis using the harness — narrate every command, every reasoning step
- Record screen+audio
- Self-review the recording — was I narrating? Did I ask clarifying questions? Did I cite sources?

### 6.2 — Devin DevBox simulation

In my real Devin trial DevBox:
- Deliberately break the env: overfill `/`, kill a daemon, set a bad MCP env var, point a config at a wrong file
- Recover, while narrating

This is closest to the actual interview. Run twice with different breakages.

### 6.3 — Pure-Linux drill

WSL Ubuntu VM with a containerized service in a bad state (you don't know which) and no hints. Debug end-to-end.

### 6.4 — K8s drill

`kind` or `minikube` cluster. A misconfigured pod (wrong image, wrong resources, wrong service-account). Debug using `kubectl debug` ephemeral containers, `crictl`, the harness's K8s knowledge.

### 6.5 — Communication drill (re-do 6.1)

Same broken Compose as 6.1, but this time:
- Ask 3+ clarifying questions BEFORE running anything
- Explain at least one trade-off explicitly
- Read at least one citation aloud

Compare to the 6.1 recording — quantify the improvement.

## Plan-mode meta-research per drill (yes, even drills)

Each drill session starts in plan mode briefly:

- **Phase 1** — confirm the drill scenario is unfamiliar (don't reuse the same broken compose)
- **Phase 2** — design the breakage (one Plan agent suggests breakages; pick one I haven't seen)
- **Phase 3** — confirm with me which breakage we're using
- **Phase 4** — write `domains/_shared/sessions/drill-log/<date>-<drill>.md` (template: scenario, expected diagnostic path, actual recording link, self-review)
- **Phase 5** — `ExitPlanMode`

The plan-mode discipline matters here too: drilling without a self-review template is just noise.

## Verification per drill

- [ ] Root cause identified within wall-clock budget (30 min default)
- [ ] Fix applied + verified
- [ ] Written incident report (auto-generated by `harness report` from the playbook trace, or hand-written)
- [ ] Self-review against the 5 evaluation criteria — score each 1–5

## After 5 drills

If average self-review score is <4/5 on any criterion, cycle that criterion-specific drill. Communication drills (6.5) often need the most repetition.

## When this is done

Move to [`phase-7-optional.md`](./phase-7-optional.md) only if there's runway left. Otherwise: do MORE drills. The interview is fluency.
